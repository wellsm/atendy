# Atendy

WhatsApp ordering agent for small food businesses. Spec: `docs/specs/mvp.md`. Plans: `docs/plans/`.

## Commands

- install: `npm install`
- local db: `npm run db:up` (Postgres 16 on localhost:54322 and DynamoDB Local on 127.0.0.1:8012 for the panel socket connections)
- dev: `npm run serve` (API) and `npm run web` (panel on http://localhost:3000; copy `packages/web/.env.example` to `packages/web/.env.local`)
- typecheck: `npm run typecheck`
- lint: `npm run prettify -- --log-level silent && npm run lint`
- test: `npm test` (uses database `atendy_tests` on the local Docker Postgres)
- admin scripts live in `packages/api/src/admin/scripts/`. Create store: `STORE_NAME="Pizzaria X" STORE_SLUG=pizzaria-x npm run admin:create-store -w @atendy/api` (inputs via env vars)
- demo data: `STORE_ID=<id> [KIND=burger] [REPLACE=1] npm run admin:seed-demo -w @atendy/api` (24h hours + menu: without `KIND` the small `DEMO_MENU` pizzeria; kinds in `DemoMenuKind`, `src/menu/demo-menus.ts`; `REPLACE=1` deletes the current menu first); `tobacco_liquor` also seeds stock items, links and opening balances through `StockRepository.importDemoStock`, archiving same-name items on reload). Image prompts: `docs/specs/demo-menu-image-prompts.md`
- store policy: `STORE_ID=<id> POLICY='{"max_item_qty":10,"min_order_cents":3000,"sop":"..."}' npm run admin:set-policy -w @atendy/api` (merges; `null` clears a key; keys in `StorePolicy`)

- web build: `npm run build -w @atendy/web` (SPA shell via TanStack Start prerender)
- API deploy (user only): `npm run deploy:dev -w @atendy/api` / `deploy:prd` (`APP_STAGE` + `packages/api/<stage>.env` from `deploy.env.example`; applies the schema to that stage's Neon); `output:dev`/`output:prd` print the URL; only `destroy:dev` exists
- web deploy (user only): `npm run deploy:dev -w @atendy/web` (S3 + CloudFront, Ez4 project in `packages/web`; copy `packages/web/dev.env.example` to `dev.env`); URL via `npm run output:dev -w @atendy/web`
- AWS logs (read-only): `AWS_REGION=sa-east-1 aws-vault exec atendy -- aws logs filter-log-events --region sa-east-1 --log-group-name <group> --start-time <ms>` (the `atendy` profile has no region). Groups: `dev-atendy-api-<function-kebab>` per HTTP handler (`dev-atendy-api-evolution-webhook-handler`), `dev-atendy-inbound-queue-handler` for bot turns (a `TurnError` there is what sent the customer `TECHNICAL_ERROR_REPLY`).
- admin screens: `/admin` (stores, health), `/admin/costs` (AI cost per order vs attendant), `/admin/conversations` (timeline with AI calls and tools), `/admin/prompt` and `/admin/<storeId>` (activation, router/model, order memory, demo menu, WhatsApp) cover most `admin:*` scripts
- stock screen (panel): `/panel/<slug>?sheet=stock` (items, entries, losses, counts, barcode; alert settings in the "Estoque" settings tab)
- POS screen (panel): `/panel/<slug>/pos` (grid/search layouts (Grade/Busca), held sales, payment, receipt, caixa: open/close, sangria, suprimento); settings "PDV" tab (layout, cash control, blind close, receipt width; payment methods live in the "Pagamento" tab)
- prospecting: `/admin/prospecting` (import leads, filter and queue them by hand or "20 melhores", the prospecting WhatsApp number, paced first-message sends, statuses; specs `docs/specs/prospecting.md` + `docs/specs/prospecting-manual.md`)
- scenario battery: `/admin/simulations` (paste YAML, validate, run against a store; results, costs, links to each conversation). Scenario format: `docs/specs/simulations.md`; first set: `docs/specs/simulation-scenarios.yaml` (`pizzeria` demo menu)

## Conventions

- Web URLs, route files and search params are English (`/panel/<slug>/menu/new?category=`); only displayed text is Portuguese.
- Web routes: public menu at `/<slug>` (root), store panel at `/panel/<slug>/...`, admin at `/admin/...`; `/` and `/panel` redirect to the active org's store. Panel links pass the slug explicitly (`params={{ slug }}` from `usePanelSlug()`).
- Styling is Tailwind classes in the components. `styles.css` holds only global base rules (e.g. button cursor), never custom classes.

- Style follows `~/Freighthero/backend/docs/code-style-rules.md`.
- Modules live in `packages/api/src/<module>/` with `schemas/`, `types.ts`, `repository.ts`, and pure helpers in their own files.
- Naming: `kebab-case` files; `snake_case` tables/columns; `PascalCase` types/enums; `camelCase` functions; `UPPER_SNAKE_CASE` constants/env vars.
- Money in integer cents. Every tenant table carries `store_id`.
- Prefer `const enum`; prefer `type` unless Ez4 requires `interface`/`declare class`.
- Throw instead of logging. No `console.log` in `src/`.
- Return early. No abstraction before three concrete cases (exception: `WhatsAppProvider`, required by the spec).

## Pitfalls

- Destructure `Service.Context` in the handler parameter, never in the body: Ez4 bundles only the services named in the signature.
- Http variables live on providers, never on `Api` (plan `docs/plans/api-provider-variables.md`): a Lambda's env is project + service + its handler's provider (+ route) variables, and a changed variable updates every Lambda that carries it. A new variable goes on the provider of each handler that reads it (directly or through a helper such as `notifyAdmin`, `asaasConfig`, `StoreWhatsApp`, `locateWithGoogle`, `phone-code.ts`); a missing one is `undefined` only on AWS/serve (tests set every variable), and `notifyAdmin` then skips silently. Code reads them from `process.env` (Ez4 puts provider variables in that Lambda's env). A function without a context (authorizers, Cloud webhook check) gets `_context: Service.Context<XProvider>` only to link its provider. Queues and the cron declare their own. Never give a `Factory.Service` variables: Ez4 lifts them to the whole service.
- Removing a column from an Ez4 schema changes only types; Postgres keeps the column. `DROP COLUMN` is manual.
- `ez4 run -- <files>` treats everything after `--` as script files. Pass admin inputs as env vars.
- `localOptions`/`testOptions` in `ez4.project.js` always point to Docker Postgres: `ez4 serve/run/test --local` create tables on that target. Never wire `EZ4_RAW_PG_DB_URL` (Neon) there; only `ez4 deploy` reads it. Admin scripts therefore run only against local data for now.
- Third-party webhook bodies must be typed `Object.Any` (`@ez4/schema`): a `Record<string, unknown>` or partial type makes the gateway validator strip fields, and handler tests (which call the function directly) do not catch it.
- `findOne` only accepts a unique key in `where`; use `findMany({ take: 1 })` for secondary indexes.
- The local queue emulator has no FIFO ordering or dedupe: debounce/echo ordering is only proven by tests and on AWS.
- Local serve runs on port 3746 (base path `/dev-atendy-api`); 3736 is used by Freighthero. Evolution: 8081, Redis: 6381.
- The customer sees "digitando…" only during the model turn (`provider.startTyping` in the inbound queue, stopped in `finally` before the reply): Evolution `POST /chat/sendPresence` holds the request open, so it is aborted, never left pending in the Lambda. Best effort; fixed replies (closed, media-only) send without it.
- Bot replies are stored as `pending:<id>` before sending and confirmed after; never send without that row (prevents double replies and false staff handoffs).
- Message style (plan `docs/plans/whatsapp-message-style.md`): a reply is a list of WhatsApp messages. The model separates them with a line `---` (`splitMessages`, `conversations/replies.ts`); the inbound queue sends each one as its own pending row, the next ones with `delayMs` (Evolution `delay`: "digitando…" first). The greeting is code (`conversations/greeting.ts`): on the first batch of an order cycle (no message inside the memory window), bot mode, store open; period by store timezone, first name from the push name; a new customer who only said hello gets three messages and no model call, anyone else one message before the reply and `greeted: true` for the model. It goes out with the reply, after the model, so a retried turn never leaves only a greeting (`hasBotReplySince` would count it); a technical handoff sends only `TECHNICAL_ERROR_REPLY`. The order summary is code too: the model writes `[[resumo]]` (`SUMMARY_TOKEN`) and `TurnResponder` swaps it for `formatOrderSummary` (`orders/summary.ts`) of the draft, else the last placed order. Formatting rules live in `STYLE_RULES` (`agent/prompt.ts`, both prompts): `*negrito*` with one asterisk, few emojis, numbered options 1️⃣–4️⃣. Fixed texts (status with the order code, closed, technical, media) carry emojis too.
- `@ez4/raw-pg` does not create databases. `atendy_tests` comes from `infra/postgres/init.sql` (runs only on a fresh volume).
- Prices and totals come only from `priceItem`/`computeTotals` via `OrderRepository`; tools ignore any price the model sends.
- Tests never call OpenRouter (LLM or Jev) or Anthropic: mock `OpenRouterClient.chat` / `AnthropicClient.chat` / `JevClient.evaluate` (or `globalThis.fetch` in client tests) with `mock.method`.
- A turn that fails after a mutating tool ran is never replayed (`TurnError.retryable = false`): the handler hands off with `TECHNICAL_ERROR_REPLY`. Retryable failures go back to the queue until `attempt === maxAttempts`.
- New queue variables need a value in the `test` script (`ez4 test` refuses missing ones).
- Jev runs through OpenRouter's Decisions API at `https://openrouter.ai/api/alpha/decisions` (no `/v1`), same key as the LLM. Both responses carry `usage.cost` in USD; that is what `ai_calls.cost_usd` stores.
- Tools act on the "current order": the draft, else the conversation's `placed` order still inside `order_memory_hours`. Writes to a placed order go through `OrderRepository.editPlacedOrder` (transaction + `lock: true` + status check); never update a placed order outside it.
- Orders in progress (plan `docs/plans/orders-in-progress.md`): a `placed` order is always edited (a "new order" goes into it). While `accepted`, `add_to_order` adds one line through `OrderRepository.addToAcceptedOrder` (locked, status re-checked, sets `amended_at`) only from the store's add-on categories (`addOnCategories`, `src/orders/in-progress.ts`: policy `add_on_category_ids`, null = drink-named categories, `[]` = none; the panel mirrors `isDrinkCategory`); the bot quotes `add_on_extra_minutes`. A new draft from the bot (`add_item`, `repeat_previous_order`) needs `OrderRepository.assertCanStartOrder`: the last placed order in the memory window must have reached `new_order_after_status` (null = `done`, one order at a time; done/canceled never block). Attendant and web orders are not gated. `last_order.new_order_allowed`/`add_on` tell the model.
- A technical handoff in the inbound queue (non-retryable or last attempt) never throws, so it sends `notifyAdmin` (Telegram: store slug, conversation id, attempt, error message; never customer text). Tests that reach it mock `fetch` and set `TELEGRAM_*` in `process.env` (other specs clear them).
- A limit that needs a person throws `OrderError` with `handoffReason`; `executeTool` hands off and marks the turn mutated. Do not hand off in the repository.
- Approval reasons (`APPROVAL_REASONS` in `conversations/types.ts`: `order_limit`, `qty_limit`, `new_customer_review`, `suspected_prank`) do not hand off: `escalate` (tools) sets `conversations.approval_reason`, the turn's reply is never sent and its batch stays pending (the inbound queue skips turns while waiting). `POST /panel/conversations/{id}/approval` sets `approved_reason` (limits lifted until the next placement) and re-queues the latest inbound message; "Assumir" hands off with the approval reason. Back to the bot (`PATCH` mode `bot`) re-opens the customer messages after the last outbound one and queues them.
- Panel auth: the store comes from the Clerk token's org (`o.id`, v1 `org_id`) via `StoreRepository.findByOrgId`; there is no custom `sid` claim. Admin routes check `ADMIN_USER_IDS` (Clerk user ids).
- `stores.active` is admin-controlled; the WhatsApp webhook drops every event of an inactive store. `accepting_orders` is the store's own switch.
- Ez4 refuses empty variables: `CLERK_JWT_KEY`, `ADMIN_USER_IDS`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `GOOGLE_MAPS_API_KEY`, `WEB_BASE_URL` need a value in `local.env` and in the `test` script.
- The bot's menu link is `storefrontUrl(WEB_BASE_URL, slug)` (`src/storefront/url.ts`), built by the inbound queue and given to the model as `store.menu_url`; the model only copies it. `WEB_BASE_URL` is the web origin per stage (local `http://localhost:3000`, dev CloudFront, prd domain). Tests sign Clerk tokens locally (`test/support/clerk.ts`) and mock `fetch` for Telegram.
- API CORS (`src/api.ts`) is a type literal: add the production web origin there when the panel is deployed.
- Panel sends (staff replies, order status messages) go through `sendStaffMessage` (`src/panel/send.ts`): pending row → send → confirm, stored as `author = 'staff'`. Never store them as `bot`: the queue's "already replied" check counts bot rows only. `claimPendingEcho` claims bot and staff pending rows.
- Order status changes from the panel go through `OrderRepository.setStatus` (locked transaction, transition table in `src/orders/status.ts`). Status first, customer message after (best effort, `notified`).
- Settings writes validate with the pure validators in `src/stores/settings.ts` (`SettingsError(field)` → 400 `context.field` via `withSettingsErrors`); hours and delivery are replaced in one transaction (`replaceHours`, `replaceDelivery`). `order_memory_hours` is admin-only (not in `PANEL_POLICY_KEYS`).
- WhatsApp instance create/connect/state/logout go through `StoreWhatsApp` (`src/panel/whatsapp.ts`), shared by the panel and `admin:connect-whatsapp`; it uses the global `EVOLUTION_API_KEY`, which never leaves the API. Sending uses the per-instance token. Evolution stores each instance's webhook URL; `connect` re-sets it (`EvolutionClient.setWebhook`) on existing instances, so after changing `WEBHOOK_BASE_URL` or the base path a reconnect from the panel fixes it (a linked instance needs a logout first).
- Menu writes from the panel go through `MenuRepository` (`createProduct`/`replaceProduct` save a product whole in one transaction and keep sent group/option ids after checking they belong to the store and to that group; categories and toggles are scoped by `store_id`). Validate with `src/menu/validation.ts` (`MenuError(field)` → 400 via `withMenuErrors`). `importMenu` is only for the demo seed and tests.
- Option groups are shared (plan `docs/plans/menu-shared-groups.md`): `product_groups` links a store's `option_groups` to products. Name, price mode, options (prices, active, photos) live on the group and change for every linked product; `min`/`max`/position live on the link (`option_groups.min/max` are only the default for the next link). Only `MenuRepository` reads these tables (`loadGroups` builds `product.groups` in the old shape, so pricing, the agent and the storefront never see links). A product save that sends another product's group id links it; groups left without links are deleted with their options; a shared group may not end with fewer options than another link's `max` (`shared_groups`). Photo cleanup uses the keys the repository returns (`droppedImageKeys`, `deleteProduct`/`deleteGroup` results), never a before/after diff of one product. `applyGroup` links (skips already linked, same-name and `MAX_GROUPS`); `updateGroup`/`deleteGroup` are the library. `importMenu` links groups with equal name, price mode and options once. `option_groups.product_id/position` are legacy (nullable, backfill only): every stage needs the plan's backfill SQL right after the deploy that created `product_groups`.
- Store LLM model ids come only from `LLM_MODELS` (`src/stores/models.ts`); the admin PATCH refuses others. Add a model there, not in the database Ids starting with `anthropic-direct/` (`ANTHROPIC_DIRECT_PREFIX`) run on Anthropic's own API with `ANTHROPIC_API_KEY` (`AnthropicClient`, `src/agent/anthropic-client.ts`, converts the OpenAI-shaped history and caches system + tools; Claude 5.5 models think by default, so each Anthropic answer keeps its raw blocks in `ChatMessage.blocks` and the next tool round sends them back unchanged, as Anthropic requires); their cost comes from `ANTHROPIC_PRICES` (same file as `LLM_MODELS`, kept by hand from Anthropic's pricing page; a direct model is listed only if it has a price). Every other id is OpenRouter (GPT only there). Only `LlmAgent.run` switches: Jev, transcription and simulations always use OpenRouter. `ANTHROPIC_API_KEY` needs a value in `local.env`, each stage env and the `test` script (a placeholder works while no store uses a direct model).
- One login can own many stores (one Clerk org each). Switching store (`StoreMenu`) and creating one with `/onboarding?new=1` clear the whole query cache; keep it that way instead of keying every query by org.
- Store billing is per order cycle (`billing_records`, `src/billing/`): the bot placing an order → 100 %; a handoff → what the AI finished in the draft (`stepsFromCart`: 10 % nothing, 40 % items, +15 % fulfillment/address/payment); `technical_error`/`send_failed` → 0 %; amount = ceil(store `order_price_cents` (null = 50) × %). Billing hooks live in `ConversationRepository.handOffToHuman`/`setMode(Human)` and the `place_order` tool: every new way to a person must go through those two. A cycle's row only goes up; amending a placed order never bills again. `billing/` must not import `conversations/` (import cycle; see the Ez4 resolve-hook pitfall).
- Attendant orders (`/panel/conversations/{id}/draft…`, human mode only) go through `OrderRepository` like the tools, with `skipLimits` and `place(…, { byStaff: true })` (no closing cutoff, no new-customer review) and never bill; a handoff where the bot never replied in the order cycle (`botServed`) bills nothing.
- A draft whose conversation got no message for longer than the order memory window becomes `abandoned` (`abandoned_at` = when the customer stopped; it leaves `conversations.draft_order_id`): `TurnResponder` checks it before reading the draft (`abandonIfStale`), `BillingDailyCron` and the closed orders list sweep the rest (`abandonStaleDrafts`). Abandoned drafts are never billed; history and thread marks show only those with items (`subtotal_cents > 0`).
- Every AI call goes through `AiCallRepository.record` (stamps `PROMPT_VERSION`, a hash of the fixed prompts and tool definitions in `src/agent/prompt-version.ts`) and, when it asked for tools, `AiCallRepository.setTools` after they run. `ai_calls.prompt_version`/`tools` were added in Admin Part 3: Neon needs that migration.
- WhatsApp media (image, video, audio, document, sticker) is stored as a labelled body (`🎤 Áudio`, `🖼️ Imagem: <caption>`; `src/whatsapp/media.ts`), like the location body; the file is not downloaded, except voice notes: the webhook keeps their raw `{ key, message }` in `messages.voice_note`; the inbound queue (any mode, before the mode check) downloads each once through `WhatsAppProvider.downloadMedia` (Evolution gets the whole message, so it needs no message store), writes it to the `VoiceNotes` bucket (`saveVoiceNotes`, `src/conversations/voice-notes.ts`, `messages.audio_key`, 90-day expiry) and clears `voice_note`; in bot mode it then transcribes the bytes (or the bucket copy, when an earlier run saved them and the turn waited) with `OpenRouterClient.transcribe` (`src/agent/transcription.ts`, `ai_calls.path = 'transcription'`). The body becomes `🎤 Áudio transcrito: <texto>` (not a caption, never media-only). The panel thread signs `audio_key` as `audioUrl` (`PanelThreadProvider`) for an `<audio>` player. Tests mock `OpenRouterClient.transcribe`, the provider's `downloadMedia` and pass a fake `voiceNotes` bucket. A batch of media without captions gets `MEDIA_ONLY_REPLY` without a model call; otherwise `bodyForModel` tells the model what it cannot open. The panel renders these bodies and the location pin via `MessageBody` (web), which mirrors both formats.
- Reactions (`reactionMessage`) are `ParsedEventKind.Reaction`, never text. The webhook puts the emoji on the reacted message (`messages.reaction`, null when removed; `ConversationRepository.applyReaction`), shown as a badge on the bubble. Only `isAnswerReaction` (`src/whatsapp/reaction.ts`: the bot's latest outbound message, containing `?`) also ingests a customer message `Reação 👍 à mensagem: <excerpt>` for the bot; everything else (status messages, staff, older messages, removals, the store's own reactions) never reaches the queue. A turn with a reaction skips Jev (`isReactionForModel` in `tryJev`): the full agent reads it against the question, and the prompt makes 👍 a "yes" only for yes/no questions (options like payment or pickup → it asks the customer to write the choice).
- Distance delivery: coordinates never pass through the model. A WhatsApp pin becomes the message body `📍 Localização: <lat>,<lng>` (`src/whatsapp/location.ts`) and `TurnResponder` stores it on the order before the turn; typed addresses are geocoded only inside `OrderRepository.setAddress` (via `ctx.geocode`). The fee comes from `delivery_bands` in `getCart`. Tests mock `fetch` for Google; `GOOGLE_MAPS_API_KEY` must be set in `local.env` (Ez4 refuses empty variables).
- Auth screens (`/sign-in`, `/sign-in/sso-callback`) are ours, built on the `@clerk/react` 6 headless "future" API (`useSignIn`/`useSignUp` from `@clerk/react`, not `@clerk/react/legacy`): email code for sign-in and sign-up (unknown email → sign-up), Google via `signIn.sso` + `HandleSSOCallback`. Keep `<div id="clerk-captcha" />` on the page or sign-up fails under bot protection.
- The web build emits three JS files (app, `vendor`, rolldown runtime): Start forces route code splitting, so `codeSplittingOptions.defaultBehavior: []` keeps routes in the app chunk, and the `vendor` group must stay `includeDependenciesRecursively: false` (Start's client entry in `node_modules` imports `src/router.tsx` and would pull the app into it). `index.html` is the SPA shell (CloudFront default object and rewrite target). `VITE_*` are baked per build: one build per stage.
- Ez4 deploy state is remote (`stateFile.remote: true`, S3 bucket managed by Ez4) and per stage: path `<stage>-deploy` in both projects (API and web). Never rename these paths after a deploy: Ez4 would treat the stage as new and recreate everything.
- `ez4 destroy` of the web CDN may fail upstream (`functionARN ... must not be null`, rewrite rule); Receivy vendors a patched `@ez4/aws-cloudfront` for it.
- Handler and authorizer function names must be unique across the whole API: Ez4 names each AWS Lambda after the function (`dev-atendy-api-update-store-handler`), so two `updateStoreHandler`s share one Lambda and one route runs the other's code and body schema. Local serve does not show it. Admin handlers carry `Admin` (`updateAdminStoreHandler`).
- The panel URL picks the store: `panel.$slug.tsx` maps the user's Clerk memberships to slugs (`GET /panel/stores?org_ids=`) and calls `setActive` on the slug's org when it is not the active one; the API still trusts only the token org. Panel-created slugs always end in `-xxxx` (`slugify`), so they never hit a static route; a `STORE_SLUG` given to `admin:create-store` must not be `panel`, `admin`, `onboarding` or `sign-in`.
- Public routes live under `/public/...` without authorizer (`src/storefront/`, `GET /public/stores/{slug}`): only `stores.active` stores, active products, no ids beyond the menu's. Web orders (`POST /public/stores/{slug}/quote` and `/orders`, `src/storefront/web-order.ts`): the cart lives in the browser; the order is built through `OrderRepository` like an attendant's (no `max_*` limits), placed with `orders.source = 'web'`, billed at `WEB_ORDER_PERCENT` (`BillingOutcome.Web`), and leaves a processed customer message so the bot never answers it; a failure deletes the half-built draft (`discardDraft`). Customers are matched by phone and its old 8-digit WhatsApp form. Status messages of web orders carry the order code and, on accept, the summary. Web orders need a verified phone: a WhatsApp code from Atendy's own Cloud API number (`src/storefront/phone-code.ts`, `whatsapp-otp.ts`, template `otp_code_pt_br_v1`) gives a signed 30-day token the browser sends as `phone_token`; `WHATSAPP_OTP_PHONE_ID=local` skips WhatsApp and returns the code (local only). Billing uses `stores.web_order_percent` (null = `DEFAULT_WEB_ORDER_PERCENT`). Meta's delivery statuses of those codes come on `POST /webhooks/whatsapp-cloud` (`src/whatsapp/endpoints/cloud-webhook.ts`, signed with `WHATSAPP_APP_SECRET` over the raw `request.data`; `GET` answers the check with `WHATSAPP_WEBHOOK_VERIFY_TOKEN`) and land on `phone_verifications.delivery_status`/`delivery_error` by `message_id`; `/webhooks/whatsapp/{storeId}` stays Evolution's. "Meus pedidos" on the public menu (`POST /public/stores/{slug}/my-orders`, token in the body) lists the confirmed phone's placed orders in that store (any source); "Pedir de novo" rebuilds cart lines in the browser at today's prices (`repeatLines`, `lib/cart.ts`) and leaves out items whose product, options or option rules changed. Order codes (`orders.code`, `src/orders/code.ts`) are given on the first placement by the store's `order_code_mode` (random: 6 symbols without 0/O/1/I/L; sequential: `stores.order_seq` + 1 under a row lock); display through `displayOrderCode` (old orders: id start, upper case), never `id.slice`. Counters that must hold under parallel requests use a locked transaction: Ez4's conditional `updateMany` + `increment` is not atomic.
- Product and option photos live in the private `ProductImages` bucket (`src/storage.ts`). Menus never expose keys: endpoints swap `imageKey` (product and each option) for a signed `imageUrl` (1 h) with `withImageUrl(s)` (`src/menu/images.ts`). Upload: `POST /panel/menu/{products|options}/{id}/image/upload` (signed PUT to `uploads/<storeId>/<target>/<id>`) → browser PUT (resized to WebP ≤ 1200 px in `lib/image.ts`) → `POST .../image` checks type/size, copies to a new `<target>/...` key and deletes the old object. Saving a product deletes the photos of options it dropped; deleting it deletes all its photos (`productImageKeys`). The form saves photos after the product (new options are matched by position in the response). Endpoints that return products use `PanelMenuProvider` (db + bucket); tests pass a fake bucket object (`BucketTester` mocks are restored between tests). Bucket CORS is a type literal like the API's: add the production web origin there too.
- Demo menu photos are not in the bucket: `importMenu` saves `image_key = 'demo-menu/<image>'`, `signImage` returns the web-relative `/demo-menu/<image>` (files in `packages/web/demo-menu/`, kept in the repo but out of the web build: `vite dev` serves them with a small plugin in `vite.config.ts`, deployed stages read them from the web's `DemoMenuFiles` bucket behind the same CloudFront on `demo-menu/*`, synced by `npm run demo-images:dev -w @atendy/web` after a web deploy; only dev gets them, prd stores upload their own), and every bucket delete goes through `isBucketImage` (the local emulator and the test mock throw on missing keys).
- After adding an Ez4 emulator package (e.g. `@ez4/local-storage`), restart `npm run serve`: a running serve answers "Service emulator not found".
- Simulations (`src/simulations/`) run the real pipeline with fake customers whose reply JID ends in `@sim`: the inbound queue sends to them through `SimulatorProvider` (no WhatsApp; the inbound `reply` queues the next `SimulationQueue` step once, after every message of the reply; the step's duplicate check and `max_bot_messages` count replies, `countBotReplies`, not messages). Customer messages enter through `ingestCustomerMessage` + `InboundQueue` like the webhook, with ids `sim:<simulationId>:<turn>:<index>` (retries never duplicate). The customer model is picked per run from `SIMULATION_CUSTOMER_MODELS` (add models there, not in `LLM_MODELS`). The simulated customer's and judge's costs live on `simulations`, never in `ai_calls`; bot costs and billing are the store's real rows. Changing the inbound flow (new reply paths, new handoff paths) must keep one bot reply per customer batch or call `handOffToHuman`, or simulations stall until `no_reply` (5 min).
- Store payments (`src/payments/`, spec `docs/specs/store-payments.md`): Asaas card subscription per store (validated
  without a charge, placeholder value). `BillingDailyCron` (06:00 BRT, idempotent; `POST /admin/billing/run` runs it)
  closes the previous calendar month on day 1 and sets the subscription's day-5 payment to the invoice amount (or
  deletes it below `MIN_CHARGE_CENTS`); records keep `invoiced_cents`, so a raise after the close bills only the
  difference. Card data goes browser → API → Asaas only: never store, log or echo it. `billing_blocked` (7 days past
  due) drops WhatsApp events like `active = false`. Tests mock `fetch` for Asaas and call `runDaily(..., [storeId])`. Admin test tools (`/admin/<storeId>` → Pagamento: run
  with a simulated date, charge the scheduled invoice today) call Asaas for real: on prd they charge the store.
  `ASAAS_API_URL`/`ASAAS_API_KEY`/`ASAAS_WEBHOOK_TOKEN` need values in `local.env` (Ez4 refuses empty variables). Same for `WHATSAPP_OTP_PHONE_ID`/`WHATSAPP_OTP_TOKEN`/`WEB_PHONE_TOKEN_SECRET`/`WHATSAPP_WEBHOOK_VERIFY_TOKEN`/`WHATSAPP_APP_SECRET`.
- Prospecting (`src/prospecting/`, spec `docs/specs/prospecting.md`) is admin-only outreach with its own webhook `/webhooks/prospecting` (authorized by the sender row's `webhook_secret`) and its own Evolution instance `atd_prospecting_*`. It never touches stores, conversations, messages, the inbound queue or billing. `ProspectingSendCron` runs every minute and sends at most one `queued` lead; imported leads are `available` and only the admin queues them. The three `prospect*` tables (`prospecting_sender`, `prospect_imports`, `prospect_leads`) reach Neon only through the user's deploy. `PROSPECTING_ENABLED=false` turns the module off per stage (`src/prospecting/enabled.ts`: cron and webhook skip the database, admin routes 404); it needs a value in every env file and the `test` script.
- Gateway bodies are camelCase in code and snake_case on the wire (`NamingStyle.SnakeCase`); the web client sends/reads snake_case.
- Stock (`src/stock/`, spec `docs/specs/stock.md`, plan `docs/plans/stock.md`): balances change only through `applyMovements` (locked transaction, items locked in ascending id; `allowArchived` only for order moves); order stock only through `syncOrderStock` (target-based against the frozen `order_items.stock_usage`, so editing or canceling an order returns exactly what it took). `OrderRepository.place` runs lock → re-check the draft → sync → `nextOrderCodeIn` → status in one transaction. A shortage throws `out_of_stock` and refuses bot/web orders only (`byStaff` is exempt, `skipLimits` is not). Sold out is computed by `StockRepository.availability`, never written to `active`; staff pricing passes `priceItem(..., { allowSoldOut })`; the public menu exposes only `sold_out` booleans, never balances. The movement history cursor is `(created_at, id)` (opaque `next`); costs are integer millicents. Panel stock UI is the sheet `?sheet=stock` (`&item=`, `&filter=low|sold_out|archived`), not routes; barcode camera uses the `barcode-detector` 3.2.2 ponyfill, loaded lazily. Digest: `StockAlertCron` runs hourly and claims `stock_alert_sent_on` in a locked transaction before sending; an Evolution request error restores the claim, any other error keeps it and calls `notifyAdmin`. The webhook drops `fromMe` messages to `stock_alert_phone` (echo guard) but never the owner's own customer messages or reactions. The tables `stock_items`, `stock_packages`, `stock_links`, `stock_movements` and the columns `order_items.stock_usage`, `stores.stock_alert_phone`/`stock_alert_hour`/`stock_alert_sent_on` reach Neon only through the user's deploy.
- Panel realtime (`src/realtime/`, `src/socket.ts`, `src/realtime-db.ts`, spec `docs/specs/panel-realtime.md`): `PanelSocket` (Ez4 `Ws.Service`, stage `panel`) tells open store panels what to refetch, never the data. The browser connects to `VITE_REALTIME_URL?token=<Clerk token>&slug=<slug>` (no headers on a WebSocket): never log that query string. `panelSocketAuthorizer` resolves the store from the token org and refuses another store's slug; connections live in the DynamoDB table `connections` (`RealtimeDb`, `store_id` index, TTL 2 h 15 min). Producers call `notifyPanel(panelEvents, storeId, triggers, conversationId?)` after their write succeeded; it swallows errors on purpose (the panel polls every 60 s while connected, at the old intervals otherwise). A new write path the panel shows (orders or conversations) must call it; its handler's provider needs `panelEvents: Environment.Service<PanelEventsQueue>` (draft endpoints use `PanelDraftProvider`). `PanelEventsQueue` posts with `Promise.allSettled` (a dead connection never retries the event). Local DynamoDB needs `AWS_REGION` and any `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` (`local.env`, `test` script; never real keys there). After a deploy, the `PanelSocket` URL (`npm run output:dev -w @atendy/api`) goes into `packages/web/dev.env` as `VITE_REALTIME_URL` and the web is rebuilt; empty means polling only.
- POS (`src/pos/`, `src/cash/`, spec `docs/specs/pos.md`, plan `docs/plans/pos.md`): a counter sale is an `orders` row with `source = 'pos'`, null `conversation_id`, optional `customer_id` (a name-only customer goes to `customer_name`). Held sales are server drafts created idempotently with a client UUID (`PUT /panel/pos/sales/{id}`); finalize is idempotent on the draft row (a non-draft sale is returned as is). Lines go through `prepareLine` (`byStaff`, `skipLimits`). Finalize = lock order → `syncOrderStock(enforce:false)` → store lock (cash) → `nextOrderCodeIn` → `accepted` if any item needs preparation (`needsPreparation`: category flag + product override) else `done`. Payments live in `order_payments` (methods = `stores.payment_methods`, incl. `voucher`). Cancel only through `POST /panel/pos/sales/{id}/cancel` (the board's cancel answers 409): it sets `canceled_at` and refunds per method into the session open at cancel time. `src/cash/` (sessions; movements `refund`, `order_cash`, `sangria`, `suprimento`) never imports `orders/`; one open session per store under the store-row lock; a closed session's report never changes (a canceled sale counts only when `canceled_at <= closed_at`). Order cash of WhatsApp/web cash orders reaching `done` is recorded only with cash control on and only once the store has opened a session before (unassigned rows are claimed by the next opening); cash control off → POS sales never attach to a session. Blind close hides cash amounts in the web only. POS writes refuse `active = false`/`billing_blocked` (`requirePosStore`). The bot's previous-order lookup and the abandon sweep ignore POS orders; no customer status messages for POS orders; POS orders are never billed. Receipts by WhatsApp go through `customerConversation` + `sendStaffMessage` + `notifyPanel`. Deploy (user only): new tables `cash_sessions`, `cash_movements`, `order_payments`; new columns `orders.customer_name/notes/discount/surcharge_cents/cash_session_id/canceled_reason/canceled_by/canceled_at/created_by/pos_label`, `order_items.discount`, `categories.needs_preparation`, `products.needs_preparation`, `stores.pos_layout/pos_cash_control/pos_blind_close/pos_receipt_width`; `orders.conversation_id`/`customer_id` become nullable (Ez4's migration emits the nullability change on update, `@ez4/pgmigration` `prepareUpdate`); all reach Neon only through the user's deploy.
